🔐 Sécurité : Signature & Authentification des Actes

Résumé des mesures de sécurité implémentées pour la protection de l'intégrité, de l'authenticité et de la traçabilité des actes d'état civil.

📅 Mars 2026 🏛️ Système SIFEC — République du Congo 📦 Modules : Naissance · Mariage · Décès

1. Chaîne de confiance — Validation d'un acte

1
Authentification de l'officier (2 facteurs)

L'officier d'état civil se connecte avec son identifiant + mot de passe. La 2FA (Two-Factor Authentication) est activable sur chaque compte pour une couche supplémentaire.

2
Vérification des droits (Gate/Permission)

Le système vérifie que l'officier possède la fonctionnalité module.acteNaissance.signature (ou mariage/décès) avant d'afficher le bouton de validation. Sans cette permission, l'accès est refusé.

3
Génération du code OTP (8 chiffres, 1 minute)

Un code OTP de 8 chiffres est généré côté serveur (random_int), stocké en base, et envoyé par SMS + e-mail sur les coordonnées enregistrées de l'officier. La date d'expiration (otp_expire_at) est fixée à 1 minute après génération.

4
Purge serveur des OTP expirés (Laravel Scheduler)

Toutes les minutes, le scheduler Laravel exécute validiteCodeOtpActeNaissance/Mariage/Deces() qui met à NULL les OTP expirés. Même si l'utilisateur bloque la minuterie côté navigateur, le serveur invalide le code indépendamment.

5
Validation OTP — contrôles serveur en cascade

Le service OtpService::validerOtpActes() effectue dans l'ordre :

  • Anti-replay : l'acte est-il déjà signé ? (approbation_mairie !== NULL)
  • OTP null ? → expiré/purgé par le scheduler
  • OTP temporellement expiré ? (otp_expire_at < now())
  • OTP correspondant ? (comparaison stricte ===)
  • CUI de l'officier présent ? (affectation active requise)
  • Signature numérique de l'officier présente ?
6
Application de la signature sur l'acte

Si tous les contrôles passent, le système grave dans la base : le CUI de l'officier, le fichier de sa signature numérique, la date/heure précise, l'OTP utilisé (conservé pour traçabilité QR), l'adresse IP de connexion, et la plateforme navigateur.

7
QR Code de vérification (URL signée Laravel)

L'acte PDF contient un QR code pointant vers une URL signée cryptographiquement par Laravel. Toute modification de l'URL invalide la signature. Le scan affiche les données directement depuis le serveur (pas depuis le PDF) : officier, OTP, IP, horodatage.

2. Mesures de sécurité implémentées

🔑

OTP à usage unique — 8 chiffres

Code généré par random_int(0, 99999999) côté serveur, jamais côté client. Valide 1 minute. Envoyé uniquement sur le téléphone/email enregistré de l'officier.

✅ Implémenté
⏱️

Expiration double (client + serveur)

Minuterie visuelle 60s côté navigateur (UX). Purge indépendante toutes les minutes par le scheduler Laravel (sécurité réelle). Les deux sont indépendants.

✅ Implémenté
🚫

Anti-replay

Un acte déjà signé (approbation_mairie ≠ NULL) ne peut plus être re-validé, même avec un OTP valide. Protection contre la double validation.

✅ Implémenté
✍️

Signature numérique de l'officier

Le fichier de signature de l'officier est vérifié avant validation. Si absent, la validation est bloquée avec un message explicite. La signature est gravée dans le PDF généré.

✅ Implémenté
🪪

CUI — Identifiant Unique d'Officier

Le CUI est requis (affectation active). Il est enregistré dans l'acte (approbation_mairie) et lié à la personne physique signataire.

✅ Implémenté
🔐

Contrôle d'accès par permission

Seuls les utilisateurs disposant de module.acteNaissance.signature (ou équivalent mariage/décès) peuvent accéder au bouton et à l'endpoint de validation. Vérification via Gate::allows().

✅ Implémenté
🌍

Validation depuis n'importe où

L'officier peut valider depuis n'importe quel appareil (téléphone, PC, tablette) et n'importe où dans le monde. L'OTP reçu sur son téléphone personnel est la liaison de confiance, pas le poste de travail.

✅ Conçu ainsi
🔍

Traçabilité forensique

À chaque validation : IP de connexion + navigateur/OS enregistrés automatiquement côté serveur. Permet une investigation en cas de litige. Visible dans la page de vérification QR.

✅ Implémenté
📱

Vérification par QR code (URL signée)

Chaque acte contient un QR code avec URL signée cryptographiquement par Laravel (URL::signedRoute()). Les données proviennent du serveur, pas du document imprimé.

✅ Implémenté
🔒

2FA sur les comptes utilisateurs

La 2FA est disponible et activable sur chaque compte. Elle ajoute une couche d'authentification à la connexion, indépendante de l'OTP de signature.

⚡ Disponible (activation recommandée)

3. Matrice des risques — État actuel

Risque / Scénario d'attaque Couverture actuelle Statut
Usurpation d'identité de l'officier
Quelqu'un se connecte avec les identifiants de l'officier		 Login + mot de passe. OTP supplémentaire envoyé sur le téléphone personnel de l'officier. Sans accès au téléphone, impossible de valider. ✅ Couvert
Replay d'un OTP déjà utilisé
Réutiliser un code OTP capturé		 otp_expire_at = NULL après validation. Anti-replay sur approbation_mairie. Le code reste en base mais ne peut plus être appliqué. ✅ Couvert
Validation hors délai
Utiliser un OTP après l'expiration d'1 minute		 Double vérification : otp_expire_at < now() côté serveur + purge scheduler indépendante toutes les minutes. ✅ Couvert
Falsification du QR code
Modifier l'URL du QR pour pointer vers de fausses données		 URL signée Laravel. Toute modification invalide la signature cryptographique et retourne une erreur 403. ✅ Couvert
Validation sans signature numérique
Signer un acte sans que le fichier de signature de l'officier soit uploadé		 OtpService vérifie $signature !== NULL avant validation. Retourne une erreur explicite si absent. ✅ Couvert
Double validation d'un même acte
Valider deux fois le même acte (avec deux OTP différents)		 Contrôle approbation_mairie !== NULL en début de validation. Retourne "Cet acte a déjà été validé." ✅ Couvert
Accès non autorisé à la validation
Un utilisateur sans rôle tente de signer		 Gate::allows('module.acteNaissance.signature') bloqué côté serveur. Retourne code 181. ✅ Couvert
Altération du PDF imprimé
Modifier le contenu d'un acte après impression		 La vérification QR lit les données depuis la base (pas le PDF). Toute altération du papier est détectable visuellement. ⚠️ Partiel
Interception OTP (réseau)
Intercepter le SMS/email contenant l'OTP		 Dépend du canal SMS (hors SIFEC). L'OTP expire en 1 minute, limitant la fenêtre d'attaque. ⚠️ Risque résiduel SMS
Hachage/intégrité du document
Prouver cryptographiquement que le PDF n'a pas été altéré		 Non implémenté. Le QR code et la signature visuelle sont les seuls marqueurs. ❌ Non couvert

4. Améliorations à envisager à l'avenir

🔴 Priorité haute

HTTPS obligatoire en production

Tout le trafic (OTP, identifiants, QR) doit transiter sur HTTPS/TLS. Sans HTTPS, les OTP et les cookies de session peuvent être interceptés sur le réseau. À configurer sur le serveur web (Nginx/Apache) avec un certificat SSL valide.

🔴 Priorité haute

Empreinte SHA-256 du document PDF

Calculer et stocker un hash SHA-256 du PDF généré au moment de la création. Afficher ce hash sur la page QR. Permettre à n'importe qui de vérifier que son exemplaire imprimé correspond exactement à l'original, en recalculant le hash du PDF téléchargé.

🔴 Priorité haute

2FA obligatoire pour les officiers signataires

Rendre la 2FA obligatoire (non optionnelle) pour tous les utilisateurs disposant de la permission *.signature. Actuellement activable, elle devrait être imposée dès la première connexion de ces profils.

🟡 Priorité moyenne

Journal d'audit immuable

Créer une table t_audit_log en écriture seule (INSERT uniquement, sans UPDATE/DELETE) enregistrant chaque action sensible : connexion, génération d'OTP, validation, annulation. Horodatage serveur, adresse IP, agent HTTP.

🟡 Priorité moyenne

Limitation du taux de tentatives OTP

Implémenter un rate limiting sur l'endpoint de validation OTP : ex. 5 tentatives incorrectes → blocage temporaire de 15 minutes. Protège contre les attaques par force brute sur le code à 8 chiffres.

🟡 Priorité moyenne

Notification de sécurité à l'officier

Envoyer un SMS/email à l'officier à chaque validation effectuée sous son identité, avec l'IP et l'horodatage. Il peut ainsi détecter immédiatement toute validation frauduleuse en son nom.

🟡 Priorité moyenne

Révocation d'OTP par l'officier

Permettre à l'officier de révoquer un OTP envoyé s'il estime que son téléphone a été compromis ou s'il n'a pas demandé de code. Bouton "Ce n'est pas moi" dans la page de gestion du compte.

🔵 Priorité basse

Signature électronique qualifiée (eIDAS)

À long terme, intégrer une PKI (Infrastructure à Clé Publique) pour remplacer la signature image par une signature cryptographique basée sur un certificat numérique qualifié, conforme aux standards internationaux (eIDAS, RFC 3161 pour l'horodatage).

🔵 Priorité basse

Historique de toutes les validations par officier

Page de tableau de bord pour les administrateurs montrant tous les actes signés par officier, avec filtres par période, module, IP. Permet de détecter des comportements anormaux (ex. 50 actes signés en 2 minutes).

5. Score de sécurité actuel

7.5 / 10

Niveau : Bon — Adapté à un système d'état civil en production

Les mesures actuelles couvrent efficacement les risques principaux : usurpation d'identité, replay d'OTP, accès non autorisé, falsification du QR code et double validation. La chaîne de confiance repose sur un OTP lié au téléphone personnel de l'officier (2FA de facto), sa signature numérique gravée dans l'acte et une URL de vérification signée cryptographiquement. Le passage à HTTPS obligatoire et l'ajout d'un hash SHA-256 du PDF permettraient d'atteindre un niveau 9/10.
